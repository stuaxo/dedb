# Architecture

The job dedb does is **run a DOSBox game under DOSEMU2**. A DOSBox game -
especially a GOG re-release - ships one or more `dosbox*.conf` files plus
an `[autoexec]` section. DOSEMU2 wants something different: a
`dosemu.conf` of `$_`-prefixed variables and a `userhook.bat` of DOS
commands. Translating the first into the second is the core of this
project. Everything else - fetching installers, caching metadata, listing
and removing what's on disk - exists to feed that translation or manage
its inputs.

## The core: `dosbox.conf` -> `dosemu.conf`

```
 dosbox*.conf ─parse─▶ raw dict ─validate─▶ DosboxConfig ─dosbox_to_dosemu─▶ DosemuConfig ─render─▶ dosemu.conf
                          │
              [autoexec] lines ──────────── autoexec_shims (Workaround pipeline) ─────────────────▶ userhook.bat
```

All of this lives in `dedb.dosbox` (`parser`, `models`, `converter`,
`inspector`) and `dedb.shims.autoexec`. It never touches the network or a
backend.

### The models are an anti-corruption layer

`dedb.dosbox.models` has two Pydantic models, and **each reflects one
side only**:

- **`DosboxConfig`** - field names, types and defaults match DOSBox's own
  `dosbox.conf`. Each field's `validation_alias` is an `AliasPath` that
  *locates* the value in the parsed INI's nested sections (`[cpu] cycles`
  -> `cycles`); the alias never renames (its leaf equals the field name,
  enforced by `tests/model_naming.py`).
- **`DosemuConfig`** - field names and units match `dosemu.conf`. Each
  field's `serialization_alias` is the real `$_var` name, and that is the
  **only** place the `$_` prefix is added (`model_dump_dosemurc` renders
  from it).

Neither model knows about the other. The single point of contact is
**`dosbox_to_dosemu(DosboxConfig) -> DosemuConfig`**, driven by the
`TRANSLATIONS` table - one entry per field that crosses, each naming its
source field, target field, and the small `_x_to_y` converter (or `None`
for a straight copy). Renames and unit changes happen there and nowhere
else. Fields DOSBox has that don't cross are listed explicitly in
`UNTRANSLATED_DOSBOX_FIELDS`.

### The autoexec pipeline

`[autoexec]` is not translated field-by-field - it is a list of DOS
commands, most of which DOSEMU2 runs unchanged. `dedb.shims.autoexec`
holds a list of **`Workaround`s**, each a one-line `shim` that rewrites
the lines it recognises, tagged with a `Severity`:

| Severity | meaning |
|---|---|
| `SUPPORTED` | rewritten to a working DOSEMU2 equivalent |
| `PARTIALLY_SUPPORTED` | still runs after the shim, but not identically to DOSBox (e.g. `MOUNT` -> `LREDIR`, `CHOICE` flags stripped) |
| `UNSUPPORTED` | no equivalent; the shim only `REM`s it out so it doesn't error (`IMGMOUNT`, overlay mounts) |

The shims run only on `userhook.bat`; real DOSBox launched via `-conf`
never sees them. **The shim is also the detector**: `diagnose_autoexec`
(behind `dedb dosboxconf --issues`) runs the same `Workaround` list and
reports every line a shim changed - so the "issues" report can't drift
from the fixes actually applied.

### Orchestration and reuse

`dedb.dosbox.converter` glues it together: `build()` returns the
`(DosemuConfig, userhook_lines)` pair, `write_outputs()` writes the two
files, `convert()` does both. The two backends reuse it rather than
re-implementing:

- **GOG** (`dedb.gog.importer`) parses the real `dosbox*.conf`(s) for
  each launch profile (`Play`, `Multiplayer Host`, ...) and converts each
  to its own `dosemu[_<slug>].conf` / `userhook[_<slug>].bat`.
- **archive.org** (`dedb.archive.importer`) items ship no `dosbox.conf`,
  so it converts DOSBox's built-in defaults and synthesises the autoexec
  (`MOUNT C .`, `cd`, run) from the item's `emulator_start`.

## Everything around it

| Area | Modules | Role |
|---|---|---|
| Backends | `dedb.core.backends`, `dedb.gog.*`, `dedb.archive.*` | Resolve a `gog://` / `archive://` reference, fetch + extract the installer/zip, write `metadata.json`. See [doc/backends.md](doc/backends.md). |
| Download pipeline | `dedb.core.downloader` | Shared "skip / redownload / refresh-metadata / fetch -> extract -> write metadata" template; backends fill the hooks. |
| Downloaded-program model | `dedb.core.local` (`LocalGame`), `dedb.core.metadata_file` (`GameMetadataFile`) | One `GameDescription` base, persisted as the `metadata.json` envelope and read back as the `dedb ls` view. |
| Metadata cache | `dedb.core.metadata_cache`, `dedb.{gog,archive}.metadata` | On-disk cache of upstream (GOG / archive.org) metadata, keyed by id. |
| CLI | `dedb.dedb.verbs` (`run` / `download` / `import` / `rm` / `refreshmetadata`), `dedb.dedb.cli` (`ls`), `dedb.dosbox.cli` (`importdosbox` / `dosboxconf`) | Thin wiring over the above. |

`dedb.core` is the framework every app (`dosbox`, `gog`, `archive`) plugs
into; apps import from `dedb.core`, never from a sibling app - except
that `gog` and `archive` both import `dedb.dosbox.converter` for the
conversion above.
